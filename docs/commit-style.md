# Commit Message Guide

커밋 메시지는 변경 이력을 빠르게 이해할 수 있도록 다음 형식을 사용합니다.

```text
<type>: <한글 요약>
```

예:

```text
feat: 그리퍼 힘 제한 설정 추가
fix: 카메라 연결 해제 시 재시도 오류 수정
docs: 워크스페이스 설치 방법 보완
```

## 기본 type

대부분의 작업은 아래 여섯 가지로 충분합니다.

- `feat`: 사용자나 시스템에 보이는 기능 추가 또는 확장
- `fix`: 잘못된 동작이나 오류 수정
- `refactor`: 외부 동작을 바꾸지 않는 코드 구조 개선
- `docs`: 문서만 변경
- `test`: 테스트 추가 또는 수정
- `chore`: 위 항목에 속하지 않는 유지보수 작업

빌드나 자동화 변경처럼 의미가 분명할 때만 다음 type을 사용합니다.

- `build`: 빌드 시스템이나 dependency 변경
- `ci`: CI 설정이나 workflow 변경
- `perf`: 동작은 유지하면서 성능 개선
- `style`: 공백이나 formatting처럼 동작에 영향 없는 변경
- `revert`: 이전 커밋 되돌리기

## 작성 규칙

- type은 영어 소문자로 작성합니다.
- 요약은 간결한 한글로 작성하고 문장 끝에 마침표를 붙이지 않습니다.
- 무엇을 했는지가 드러나는 구체적인 표현을 사용합니다.
- 한 커밋에는 하나의 논리적 변경만 담습니다.
- 변경 성격이 섞이면 가장 중요한 목적을 기준으로 type을 선택합니다.
- scope는 구분 가치가 있을 때만 선택적으로 사용합니다.

```text
feat(gripper): 파지 힘 제한 설정 추가
fix(camera): 연결 해제 후 재시도 상태 초기화
```

단순한 저장소에서는 scope를 억지로 붙이지 않습니다.

## 선택 기준

- 새 동작이 생기면 `feat`
- 기존 동작이 잘못되어 고치면 `fix`
- 동작은 같고 내부 구조만 바꾸면 `refactor`
- 문서만 바꾸면 `docs`
- 테스트만 바꾸면 `test`
- 분류 가치가 낮은 저장소 유지보수는 `chore`

판단이 애매할 때 새로운 type을 만들지 말고 위 기본 type 중 가장 가까운 것을 사용합니다.

## 본문이 필요한 경우

작은 커밋은 제목 한 줄로 충분합니다. 다음 정보가 제목만으로 드러나지 않을 때만 빈 줄 뒤에 본문을 추가합니다.

- 변경 이유
- 안전 또는 호환성 영향
- 중요한 제약과 trade-off
- 실행한 검증 또는 남은 위험

커밋 메시지에 파일 목록이나 diff 내용을 그대로 반복하지 않습니다.
